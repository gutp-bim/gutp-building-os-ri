# Parquet の値カラムをテキスト中心に減らせるか（#348 スパイク記録）

**結論: 減らさない。** ただし「列数が減るから軽くなる」という当初の直感も、最初に出した計測も、
どちらも誤りだった。本書は**結論だけでなく、計測が一度棄却された経緯**を残す。再測定する人が
同じ落とし穴を踏まないことの方が、結論そのものより価値がある。

関連: #348、[ADR-0006](../adr/0006-non-numeric-telemetry-value.md)、
[oss-warm-parquet-lake.md](./oss-warm-parquet-lake.md)

## 問い

Parquet レイクの値カラムは現在 4 つある
（`ParquetTelemetrySerializer.cs`: `value` double? / `value_type` string / `value_text` string /
`value_bool` bool?）。これをテキスト中心に集約すれば、汎用性が上がり列数も減るのではないか。

## 最初の計測は棄却された

最初のハーネスは 200,000 行 × 複数スキーマを本番と同じ Parquet.Net + Zstd で書き、
`text_only_R` の悪化は **+0.11%** と報告した。この数値は**使ってはいけない**。

**行生成器が全アナログ値を丸めていた。** `Math.Round(x, 1)` 等で丸めた値を使っており、
「float32」セットも**丸め済みの値**を float にスナップしていたため、両セットとも distinct 値が
**16,209 個**しかなかった。Parquet の dictionary/RLE 圧縮はカーディナリティに極めて敏感なので、
**高カーディナリティの値カラムを一度も測っていなかった**ことになる。

実際の取込経路に丸めは無い（`proto/gateway_ingress.proto` の `double value_num` →
`GatewayIngressService` → `TelemetryValueKind.Apply` → `JsonElement.TryGetDouble`）。
BACnet REAL はフルマンティッサの double としてレイクに届く。

## 訂正後の数値

値モデルだけを差し替えた一変数感度分析（ポイントカタログ・`time`・`id`・順序・他の全カラムは同一）:

| 値モデル | distinct 値 | `current` B/row | `text_only_R` B/row | 悪化 |
|---|---:|---:|---:|---:|
| 丸め済み（棄却された計測） | 16,209 | 2.383 | 2.386 | +0.11% |
| **未丸め double（実態）** | 195,160 | 7.814 | 8.335 | **+6.67%** |
| **生 float32（真の BACnet REAL）** | 191,668 | 4.128 | 6.157 | **+49.16%** |

過小評価の倍率は**どの数値を基準に取るかで変わる**ので、両方書いておく。

- 上の表の `text_only_R` 同士で比較すると、丸め済み +0.11% に対し未丸め double は **約 61 倍**、
  生 float32 は **約 447 倍**
- 棄却された計測は別に「bacnet_float32」セット（これも丸め済みの値を float にスナップしたもの）で
  +2.21% と報告していた。その数値に対しては **約 22 倍**

いずれにせよ、テキスト化に反対する根拠は測ったつもりだったものより**桁違いに強い**。

## 撤回した主張

| 主張 | なぜ誤りか |
|---|---|
| 「テキストは常に大きい」 | 丸め済み/低カーディナリティでは **0.08〜1.37% 小さい**ことすらある。+0.11% は圧縮ノイズで、無関係な変更で符号が反転する |
| 「KPI は約 19 倍の余裕がある」 | 丸め済みデータで測った値。現実的な値モデルでは余裕は **2.6〜3.6 倍**（予算の 27.8〜38.9% を使用）にとどまる |
| 「読み取りコストが決め手」 | **ノイズ床に埋もれる**（下記） |

### 読み取りコストの論拠も撤回した

最初の測定は本番経路を再現していなかった。`Datetime = rowTime.ToString("O")`
（`ParquetLakeScan.cs`）と、行ごとに datetime 文字列を **2 回**再パースする実際の
`TelemetryAggregator` が欠落していた。さらに「対照実験」は負荷のかかったマシンで
**別ブロックの最小値を引き算**しただけで、ペア測定ではなかった。

実 `BuildingOS.Shared` コードを使い、交互 ABAB・25 回ペア測定で取り直した結果:

| | 差 |
|---|---|
| 200k 行オブジェクトの A/B | **−0.11% 〜 +1.94%** |
| A/A ノイズ床 | −0.73% 〜 +1.43% |
| 単一ポイントクエリ（`GET /telemetries/query` の実形状） | +1.2% 〜 +2.3%（約 116ms 中の約 2ms） |

3 データセット中 2 つは A/A と統計的に区別できない。**読み取りコストはこの判断の材料にならない。**

## 「列数を減らす」動機は成立しない

各カラムの限界コスト（11 カラムのファイルと、そのカラムだけ抜いたファイルの差分）:

| 抜いたカラム | Δ B/row |
|---|---:|
| `value` | **1.898** |
| `id` | 0.444 |
| `point_id` | 0.025 |
| `value_type` | 0.0011 |
| `value_text` | 0.0006 |
| `value_bool` | 0.0005 |

削減候補の 3 カラムは合計 **0.002 B/row**（全体の 0.1% 未満）。Parquet は全 null カラムを
null カウント + RLE でほぼゼロコストに畳むため、「カラムが多い＝重い」は成立しない。

加えて `value_type` は捨てられない。文字列 `"true"` と真偽値 `true`、`"21.5"` と `21.5` が
区別できなくなるため、テキスト化しても実質 4 → 2 カラムにしかならない。

## 「汎用性」は方向で逆を向く

- JSON 的な意味（任意の型が入る）→ テキスト有利
- データレイク的な意味（DuckDB/Spark/pandas から型付きで読める）→ 型付き有利

`Tools/e2e-performance/quality_checker.py` が DuckDB で

```sql
WHERE point_id IS NOT NULL AND time IS NOT NULL
  AND (value IS NOT NULL OR value_text IS NOT NULL OR value_bool IS NOT NULL)
```

を実行しており、既にリポジトリ内に後者の消費者が存在する。しかもこの消費者は**3 つの値カラムを
すべて型付きで読んでいる**ので、テキスト単一列にすると型ごとの分岐が消える代わりに全消費者が
CAST を書くことになる。実測が示したのは、**その汎用性の対価が数値カラムで最大 49% の容量増**
だということ。

## 再測定する人へ

1. **値モデルを丸めないこと。** これが最初の計測を無効にした唯一の原因。
2. **読み取りコストは交互 ABAB のペア測定で、A/A ノイズ床と併せて出すこと。** 別ブロックの
   最小値の引き算は、負荷のあるマシンではブロック間ドリフトを測っているだけになる。
3. **本番の materialization 経路を通すこと**（`ToString("O")` と実 `TelemetryAggregator`）。
   自前の `foreach` は分母を半分近く小さく見せる。

ハーネスは使い捨てで、リポジトリには含めていない。上記 3 点さえ守れば再現は難しくない。
