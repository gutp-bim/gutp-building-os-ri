ガイドラインが必須と明記する最低要件は、15項目すべてを満たしています (△の2件も、管理者操作を起点とした運用で機能自体は達成できています)。一方で推奨要件は 12項目中7項目が未対応で、充足率が大きく落ちます。この差の理由は次節のとおりです。

なぜ「推奨」だけ落ちるのか — Building OS の位置づけ

ガイドラインはスマートビルをフィールド層 / データ共有・管理層 / アプリケーション層に 分けて記述します。Building OS OSS Edition はこのうち 「データ共有・管理層の中間基盤」に相当し、上下の層は意図的に持ちません。

フィールド層 — 持たない

連携ゲートウェイ(連携GW)そのものは実装しません。GW 実装は nexus-gateway 等の隣接リポジトリの責務で、本リポジトリが持つのは その受け口(gRPC GatewayIngress / GatewayEgress、MQTT / Hono コネクタ)です。

データ共有・管理層 — ここ

取り込み・正規化・保存(Hot / Warm / Cold)・デジタルツイン・API・認可までを担います。 必要要件が全項目埋まっているのはこの層に集中しているためです。

アプリケーション層 — 持たない

BEMS アプリや分析アプリのユースケースは実装しません。REST / gRPC API と権限モデルを提供し、 その上に載るアプリは利用者側の責務です。

未対応の推奨要件(連携システムのデータガバナンス、汎用ブローカー機能、位置情報、機器間関係、 ゾーングルーピング等)は、この境界の外側か将来拡張に委ねた設計判断です。 実装の抜けというより、スコープの絞り込みが表に出たものと読んでください。

※ 全体構成は アーキテクチャ、層構造の詳細は oss-tier-architecture.md、 オントロジーの標準対応は standard-mapping.md を参照。

表6: データ管理モジュール

#機能必要/推奨状態実装
1リアルタイムデータ管理機能 必要 ✅ 対応 NATS KV(telemetry-latest、history=1 = 監視点ごとの最新値、 NatsKvLatestStore)に集約・保存し、GET /telemetries/query?latest=true で 監視点 ID から特定可能。注釈: (a) 原文の「時刻…を指定した問い合わせ」は この hot 層単体では不可(IHotTelemetryStore.GetAsync に時刻引数がなく、 OssTelemetryQueryRouter は時刻範囲指定時は常に warm/cold へルーティング) —— 時刻指定問い合わせは隣接する表6-2(アーカイブ)が担う役割分担です。 (b) 「受信日時」は独立したメタデータではなく、デバイス時刻と受信時刻フォールバックが 単一の Datetime フィールドに混在します (GatewayIngressService.NormalizeTimestamp、既知の課題として #418 で言及済み)
2アーカイブデータ管理機能 推奨 ✅ 対応 Parquet レイク(MinIO、warm/cold)、CompactionWorker / LakeRetention
3連携システム情報管理機能 必要 △ 部分対応 フィールド層 GW の接続情報レジストリ(IGatewayConnectionRegistry)はありますが、 アプリケーション/プラットフォーム側の接続先・認証情報を管理する専用レジストリは ありません。近い機能として OIDC クライアント管理(OidcClientsController)がありますが、 これは Building OS へ「入ってくる」認証の管理であり、ガイドラインが指す 「連携システムの一覧・接続先」とは向きが異なります
4連携システムデータ管理機能 推奨 ❌ 未対応 外部アプリ/プラットフォームが保有するデータを Building OS 側に保存・管理する仕組みはありません

#要件必要/推奨状態実装
1空間・物体・監視点の3概念＋関係性を表現できること 必要 ✅ 対応 sbco:Room(空間)/ EquipmentExt(物体)/ PointExt(監視点)+ locatedIn / hasPoint
2空間同士の関係性を表現できること 必要 ✅ 対応 ガイドライン本文が示す具体例(図14)は「建物→フロア→部屋」の木構造 (空間トポロジー)であり、sbco:hasPart(Site→Building→Level→Room)が満たします。 「間仕切り変更等に応じた動的な変更」は本文でも「望ましい」(推奨相当)止まりで、 Twin import(replace/append)で対応可能。なお、部屋同士の隣接関係 (ドアで繋がっている等の横方向トポロジー)はこの要件の対象外で、ガイドラインの最低要件を 超える拡張として #440 で別途提案しています
3空間と物体の関係性を動的に変更できること 必要 ✅ 対応 Twin import(replace/append)により locatedIn の再構成が可能
4オブジェクトはプロパティ(データ項目)を持つこと 必要 ✅ 対応 sbco:id / name / pointType 等、bos:dataType 等
5空間・物体・監視点のグループ化(グラフ構造が推奨) 推奨 ❌ 未対応 Zone / Area に相当するクラスがありません。関係はすべて木構造(hasPart / locatedIn)です
6物体同士の関係性を表現できること 推奨 ❌ 未対応 Equipment ↔ Equipment の関係述語(Brick の feeds / isFedBy 相当)が存在しません
7オブジェクトが「位置情報」プロパティを持つこと 推奨 ❌ 未対応 生きているモデルには存在しません。自動生成 DTDL エンティティ(Dtdl.Site.*.cs)に RefLatitude / RefLongitude がありますが、リポジトリ全体で どこからも参照されない未使用コードです(下の「追加検証 2」)

作成時の追加検証

対応表を実コードで裏取りする際に見つかった、根拠の精度に関する補足です。 判定(✅/△/❌)はいずれも変わりません。

1. 表5-3 の根拠には GatewayIngressService も併記されるべき

表の「実装」列が挙げる ProtocolConnectorBase は、それ自身の doc comment のとおり HvacConnectorWorker / ElectricConnectorWorker にのみ適用されるもので、 取り込みの正本経路である gRPC GatewayIngress はこの基底クラスを通りません。 その GatewayIngress 側の skip 条件は「gateway_id/point_id 欠落」「ゲートウェイ ID 同一性(#296)」 「未知の point_id」「ツイン上の所有権」「建物階層への接続(#292)」の5つのみで、 値レンジ検証は存在しません。つまり ❌ 判定は正本経路でも同様に成り立ち、 根拠としてはこちらを挙げる方が正確です。

2. 表9-7 は「プロパティが未参照」より強く言える

RefLatitude / RefLongitude の出現箇所は JSON Schema (Defines/Schemas/dtdl.json)と、そこから生成された Defines/Entities/Dtdl.Site.Properties.cs / Dtdl.Site.Validate.Object.cs のみで、 latitude / longitude は DotNet・web-client・fixtures のいずれにも 他に現れません。さらに正確には、生成された Dtdl.Site.* 型そのものが Defines/Entities/ の外から一切参照されていません。加えて当該2プロパティは dtdl.json 上 required 指定であり、スキーマ上は必須でありながら実行時にはどの経路からも 使われていない、という状態にあります。
